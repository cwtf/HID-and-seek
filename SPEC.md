## 1. Overview

**HID & Seek** is an Android app that turns the phone into a Bluetooth keyboard for other
devices (PC, Mac, Linux, tablets, consoles, TVs, embedded/KVM gear). Text is composed on the
phone — using the phone's own soft keyboard, or generated by an LLM — and delivered to the
connected host as real HID keystrokes, indistinguishable from a physical keyboard.

Two things make it more than a remote keyboard:

1. **Staged vs. live typing.** Compose a block of text and fire it in one go, or have every
   settled edit stream to the host as you type.
2. **An LLM chat tab.** Talk to a model (OpenRouter, DeepSeek, OpenAI, or any OpenAI-compatible
   endpoint), then send its answer — or one code block from it — to the host as keystrokes.
   Optionally let the agent type directly.

### 1.1 Primary use cases

| # | Scenario |
|---|---|
| U1 | Typing long passwords / config strings / license keys into a machine with no easy input |
| U2 | Driving a headless or KVM-attached box, BIOS/UEFI screens, install prompts |
| U3 | Typing into a smart TV, console, or set-top box search field |
| U4 | Asking an LLM for a shell command or snippet and pasting it into the host without a network path on the host |
| U6 | Photographing an error or BIOS screen on the host, asking the model what it means, and typing the fix straight back over HID |
| U5 | Accessibility — composing text comfortably on a phone and delivering it to a desktop |

### 1.2 Non-goals (v1)

- No custom in-app soft keyboard. The system IME is used; the app only stages text.
- No mouse/pointer HID reports (see §12).
- No USB HID gadget mode (requires root/custom kernel — see §3.2).
- No file transfer, clipboard sync, or screen mirroring.
- No on-device LLM inference.
- No non-image LLM chat attachments (PDFs, documents, audio) — images only (§6.2.3).
  The Type screen may import decoded text files into its staging buffer (§5.3.1).
- No Play Store distribution in v1 — sideload / self-signed APK (§2.2).

### 1.3 Platform constraint on concurrent connections

Android's `BluetoothHidDevice` profile supports **one connected host at a time** — the AOSP HID
Device service tracks a single device, and connecting a second host tears down the first. There
is no supported simultaneous multi-host path on stock Android.

Accordingly, "multiple devices" is realised as **user-driven device selection**: the app remembers
every host you've used, and you pick which one to connect to — including adding a new one — from a
picker that's one tap away on every screen (§4.3.1). Switching hosts takes one tap and preserves
your staged text. Sequential broadcast to several hosts is available for the "send this to all my
machines" case (§5.3.4).

### 2.1 Min SDK rationale

Chosen by capability, not by market share.

| Requirement | API needed |
|---|---|
| `BluetoothHidDevice` profile (the whole app) | **28** |
| `FOREGROUND_SERVICE_TYPE_CONNECTED_DEVICE` | 29 |
| Runtime Bluetooth permissions `BLUETOOTH_CONNECT` / `SCAN` / `ADVERTISE` | **31** |
| `neverForLocation` scan flag — lets us skip location permission entirely | **31** |
| Dynamic color / Material You, which M3 Expressive theming leans on | **31** |
| `POST_NOTIFICATIONS` runtime permission | 33 (conditional — no min impact) |
| Predictive back | 33+ (progressive enhancement) |

**minSdk 31.** Going below 31 forces a dual Bluetooth permission path (legacy `BLUETOOTH` /
`BLUETOOTH_ADMIN` plus a location permission for scanning on 29–30), which is both more code and
a worse privacy story — the app would have to ask for location to find a keyboard host. 31 also
gives dynamic color natively rather than as a fallback. Nothing in the spec needs 32+, so there's
no reason to go higher.

## 3. HID subsystem

### 3.1 Bluetooth HID Device (primary transport)

The app registers itself as a Bluetooth HID Device (keyboard) via
`BluetoothHidDevice.registerApp()` with:

- **`BluetoothHidDeviceAppSdpSettings`** — name `HID & Seek`, description, provider,
  subclass `SUBCLASS1_KEYBOARD`, and the report descriptor below.
- **QoS** — defaults for both in/out.

#### 3.1.1 Report descriptor

Standard 8-byte boot-protocol keyboard report, plus a Consumer Control collection for media keys
(used by macros, §5.6):

```
Report ID 1 — Keyboard
  byte 0   : modifier bitmask (LCtrl, LShift, LAlt, LGui, RCtrl, RShift, RAlt, RGui)
  byte 1   : reserved (0x00)
  byte 2-7 : up to 6 concurrent HID usage codes (Keyboard/Keypad page 0x07)

Report ID 2 — Consumer Control
  16-bit usage code (Consumer page 0x0C) — volume, play/pause, browser keys
```

Output reports (host → device) carry LED state (Caps/Num/Scroll Lock); the app parses these in
`onSetReport` / `onInterruptData` and reflects Caps Lock in the UI so casing stays correct (§3.4.3).

#### 3.1.2 Connection lifecycle

| State | Meaning | UI treatment |
|---|---|---|
| `UNREGISTERED` | Profile proxy not obtained or app not registered | "Bluetooth keyboard unavailable" |
| `REGISTERED` | SDP record published, discoverable as a keyboard | "Ready to pair" |
| `CONNECTING` | `connect(device)` in flight | Expressive loading indicator |
| `CONNECTED` | Interrupt channel open, reports deliverable | Filled connected chip + device name |
| `DISCONNECTING` / `DISCONNECTED` | — | Reconnect affordance |

Behaviours:

- **Foreground service** (`connectedDevice` type) holds the connection while typing, with a
  persistent notification showing the active host and actions: Disconnect, Release all keys,
  Stop live typing.
- **Auto-reconnect** on unexpected disconnect: exponential backoff 1 s → 2 → 4 → 8, cap 30 s,
  give up after 5 min, when enabled for that device.
- **Registration released** when the app is backgrounded with no active session and
  "Stay registered in background" is off, so the phone stops advertising as a keyboard.

### 3.2 USB HID gadget (out of scope, documented)

Android can't act as a USB HID device without kernel ConfigFS access (`/config/usb_gadget`),
which requires root. The transport interface in §3.3 is shaped so a `UsbGadgetTransport` could be
dropped in later. Not built in v1.

### 3.3 Transport abstraction

```kotlin
interface HidTransport {
    val state: StateFlow<TransportState>
    suspend fun connect(target: HidTarget): Result<Unit>
    suspend fun disconnect()
    suspend fun sendKeyboardReport(report: KeyboardReport): Result<Unit>
    suspend fun sendConsumerReport(usage: Int): Result<Unit>
    val hostLedState: StateFlow<LedState>
}
```

`BluetoothHidTransport` is the only v1 implementation. `FakeHidTransport` backs unit tests and a
developer "dry run" mode that logs reports instead of sending them.

### 3.4 Text → keystrokes

#### 3.4.1 Pipeline

```
String → Grapheme splitter → KeyLayout mapping → List<KeyStroke> → Report pacer → HidTransport
```

- **KeyStroke** = `(modifiers: Int, usage: Int, holdMs: Int)`.
- Each stroke emits a **key-down report** then a **key-up (all-zero) report**. A missing key-up
  causes runaway repeat on the host, so this pairing is enforced by construction.
- The pacer runs on a dedicated single-threaded dispatcher with a configurable inter-key delay.

#### 3.4.2 Keyboard layouts

The host decodes HID usage codes through **its own** layout, so characters must be mapped using
the layout the *host* is configured for. Per-device setting, default **US QWERTY**.

**v1 ships US QWERTY and US-International only** (open question #4 resolved toward shipping
sooner); the layout system is data-driven from day one so others are pure content additions.
Planned next: UK, German (QWERTZ), French (AZERTY), Spanish, Italian, Nordic, Portuguese, Turkish-Q.

```json
{
  "id": "de_DE",
  "name": "German (QWERTZ)",
  "map": { "z": {"usage": 28}, "y": {"usage": 29}, "@": {"usage": 20, "mods": ["RALT"]} },
  "deadKeys": { "´": {"usage": 46, "mods": []} }
}
```

Unmappable characters (emoji, CJK, anything outside the layout) follow the **Unmappable character
policy** setting:

| Policy | Behaviour |
|---|---|
| **Skip** (default) | Drop it, count it, warn after send |
| **Unicode escape** | Host-specific sequence (Linux: `Ctrl+Shift+U` + hex + Enter; Windows: `Alt`+numpad decimal, needs numpad + registry key; macOS: unsupported → skip) |
| **Substitute** | Replace with a configurable ASCII fallback (e.g. `?`) |

The send preview (§5.3.2) shows exactly which characters will be dropped **before** sending.

#### 3.4.3 State hazards

- **Caps Lock**: if the host reports Caps Lock on, the mapper inverts letter shifting. Without LED
  state, a manual "Host Caps Lock is on" toggle is offered.
- **Num Lock**: required for Alt-code escapes; the app warns rather than toggling it.
- **Dead keys**: composed characters emit `deadKey + base` with extra delay so host compose logic
  keeps up.
- **Auto-indent hazard**: editors that auto-indent mangle typed code. "Strip leading whitespace"
  (§5.3.3) is on by default for text originating from chat code blocks.

#### 3.4.4 Keystroke timing

Every keystroke is paced. A single character is at minimum four timed events:

```
[modifier down] ──settle──> [key down] ──hold──> [key up] ──inter-key──> [next key]
```

All four intervals are user-configurable (§7.3.1). Defaults:

| Setting | Default | Range | Purpose |
|---|---|---|---|
| **Inter-key delay** | **12 ms** | 0–200 ms | Gap between one keystroke completing and the next starting. The main throughput dial (~60 chars/s at 12 ms). |
| **Key hold time** | 8 ms | 0–50 ms | How long a key is held down before the key-up report. Some hosts, KVMs, and BIOS firmware ignore keys released too quickly. |
| **Modifier settle time** | 5 ms | 0–50 ms | Pause after asserting Shift/Ctrl/Alt/Gui before the key it modifies, so the host sees the modifier first. |
| **Extra delay after newline** | 40 ms | 0–500 ms | Hosts often do work on Enter (submit, re-render, scroll) and drop input during it. |
| **Extra delay after dead key** | 25 ms | 0–200 ms | Gives host compose logic time to resolve `deadKey + base`. |

This is a **per-character** delay applied to every send path — staged, live, clipboard, macro, and
agent typing alike.

**Profiles** bundle the five values so they don't have to be set individually:

| Profile | Inter-key | Hold | Newline | Suits |
|---|---|---|---|---|
| `Fast` | 5 ms | 5 ms | 20 ms | Modern desktops, short text |
| `Normal` (default) | 12 ms | 8 ms | 40 ms | Almost everything |
| `Safe` | 30 ms | 15 ms | 100 ms | Flaky Bluetooth, busy hosts, remote desktop sessions |
| `BIOS` | 60 ms | 25 ms | 120 ms | UEFI/BIOS, KVM switches, embedded firmware, boot-protocol-only hosts |

Profiles are **per-device** (§7.2), so a KVM'd lab box can sit on `BIOS` while a laptop stays on
`Fast`, with no switching by hand.

**Humanize** adds ±jitter (Gaussian, σ = 30% of the inter-key value, clamped to ≥0) for hosts or
software that reject machine-perfect timing.

> **Field finding (first real-device test).** Repeated identical characters were
> arriving halved — `ssss` as `ss` — because the gap between releasing a key and
> pressing it again was too short for the host to tell a repeat from key-repeat
> chatter. Hence `repeatedKeyExtraDelayMs`, applied only when consecutive
> strokes share a usage code. On the host tested, **repeats were only fully
> reliable at the BIOS profile's 100 ms**; 30 ms (Normal) improved matters but
> did not fix them. The defaults are unchanged pending more hosts to compare —
> if this proves general rather than host-specific, Normal should rise toward
> 60–100 ms. Note the general inter-key delay was *not* the problem: ordinary
> text was unaffected throughout.

Timing is enforced on the HID dispatcher using monotonic scheduling rather than naive `delay()`
accumulation, so a slow Bluetooth write doesn't compound into progressive drift across a long send.

### 3.5 Sending semantics

- Sends are cancellable mid-flight; cancel immediately emits an all-zero report to release held
  modifiers.
- Progress reported as characters sent / total, with a linear progress indicator.
- Sends are serialized; a second send while one is in flight is queued.
- **Panic key** — "Release all keys" in the notification and on the Type screen.

## 5. Feature specifications — HID typing

### 5.1 F-HID-01 · Device roster

- Every host the user connects to is remembered: name, MAC, nickname, layout, typing profile,
  host OS tag, auto-reconnect flag, last-connected time, characters sent.
- Roster is unlimited; picker sorts by last-connected desc, with the active device pinned.
- One device may be marked **default** — auto-connected on launch if "Connect on launch" is on.
- MAC addresses are stored in the app's encrypted store.

### 5.2 F-HID-02 · Selecting and adding devices

#### 5.2.1 Selecting

- Any known device is connectable in one tap from the picker (§4.3.1).
- Switching hosts disconnects the current one first; the staged buffer, the sent watermark reset,
  and the chat session all survive the switch.
- Failure to connect within 15 s → inline error on the row with **Retry** and
  **Open Bluetooth settings**.

#### 5.2.2 Adding

"Add a device" opens a guided sheet, because HID pairing is backwards from what users expect —
the *host* initiates, since the phone is the keyboard:

1. **Step 1 — Make discoverable.** The app registers the HID profile and requests discoverability,
   showing a countdown and the name the phone advertises.
2. **Step 2 — Pair from the host.** Plain-language instructions per host OS (selectable tabs:
   Windows / macOS / Linux / Android / TV), e.g. *"On Windows: Settings → Bluetooth & devices →
   Add device → Bluetooth → pick **HID & Seek**"*. A live list shows incoming pairing requests.
3. **Step 3 — Confirm.** Passkey confirmation if the host requests one.
4. **Step 4 — Configure.** Nickname, keyboard layout, host OS tag, typing profile — with a
   **Test typing** button that types `HID & Seek test 123` into the host so the layout can be
   verified immediately.

Already-paired devices that the app hasn't seen are also listed (from
`BluetoothAdapter.getBondedDevices()`, filtered to plausible HID hosts) so they can be adopted
into the roster without re-pairing.

### 5.3 F-HID-03 · Staged send

#### 5.3.1 Buffer
- Backed by `TextFieldState`; survives process death via `SavedStateHandle` + debounced (500 ms)
  DataStore autosave.
- **Snippets**: save the buffer under a name; snippet list in the Type overflow. Snippets marked
  *sensitive* keep their text in the encrypted store rather than the settings file, never appear
  in previews, exports, or logs, and apply `FLAG_SECURE` while loaded — the text is on screen
  precisely because it is about to be typed somewhere, which is the worst moment to be captured.

- **Text-file import**: the system document picker loads UTF-8 or BOM-marked UTF-16 into the
  staged buffer. Imports are limited to 256 KiB and binary control data is rejected. The source
  file is not copied, retained, or transferred; only its decoded text is emitted as HID keys.

#### 5.3.2 Preview
Bottom sheet showing the keystroke sequence grouped per line, unmappable characters highlighted
with the applied policy, estimated duration at the current profile, and warnings (leading
whitespace, unknown Caps Lock state, >5,000 chars).

#### 5.3.3 Send options (per-send, remembered)
Append Enter · Strip leading whitespace · Normalize line endings (LF/CRLF/CR) · Trim trailing
whitespace · Tabs → N spaces.

#### 5.3.4 Broadcast send
Select N devices from the picker in multi-select mode; the app connects, sends, disconnects, and
moves on, showing a per-device result list. Abort stops after the current device. Labelled
explicitly as sequential.

### 5.4 F-HID-04 · Live typing — buffer-first

**This is the core behavioural change from v0.1, and it removes the autocomplete problem entirely.**

Live mode does not intercept keystrokes. Everything the IME does — predictive text, gesture
typing, autocorrect, CJK composition — lands in the **staging buffer first**, exactly as in Staged
mode. A background drain loop then transmits *settled* buffer content to the host. The buffer is
the single source of truth; the host is a replica that lags it slightly.

#### 5.4.1 Model

```
buffer:     "sudo systemctl restart ngin|x"
                                        ↑ composing region (not yet settled)
sentIndex:  23   ──────────────────────┘
            └─ everything before this has been typed on the host
```

Two pieces of state: the buffer text, and `sentIndex`, a watermark for how much has reached the
host.

#### 5.4.2 Drain rules

1. **Never transmit inside an active composing region.** Pending text is
   `buffer[sentIndex until compositionStart]` (or to the end when there's no composition).
   Autocorrect and swipe candidates mutate the composing region freely and cost nothing.
2. **Settle delay.** The drain waits for a quiet period with no buffer edits before flushing
   (default **400 ms**, user-configurable 0–2,000 ms — §7.3.2). Fast typists produce a few large
   flushes instead of a keystroke storm.
3. **Immediate flush triggers**, bypassing the settle delay: pressing Enter, pressing Space after
   a word boundary, tapping **Catch up now**, or the pending region exceeding a threshold
   (default 120 chars). Each trigger is individually toggleable (§7.3.2).
4. **Retraction on divergence.** If an edit changes text *before* `sentIndex` — autocorrect
   rewriting an earlier word, a backspace, a mid-text edit — the drain computes the longest common
   prefix `k` between what was sent and the current buffer, emits `sentIndex − k` **Backspace**
   keystrokes, sets `sentIndex = k`, and re-drains forward. The host converges on the buffer.
5. **Retraction cap** (default 64 chars, user-configurable 0–500 or Unlimited — §7.3.2). A
   divergence deeper than the cap pauses the drain and asks: **Retype from here** (accepting a long
   retraction), **Skip and resync** (move `sentIndex` to the current buffer end, leaving the host
   out of sync — clearly warned), or **Stop live typing**. The over-cap response can be made
   automatic in settings for users who don't want the prompt.
   Retraction assumes the host caret is where the app left it; if the user has clicked elsewhere on
   the host, retraction will delete the wrong text. The cap and the confirmation prompt exist
   precisely to bound that blast radius.
6. **Disconnect.** The drain pauses; the buffer keeps accumulating and everything past `sentIndex`
   is queued. On reconnect, either resume the drain or reset the watermark to the buffer end
   (setting; default = ask).
7. **Mode switch.** Live → Staged keeps `sentIndex`; the remaining pending text is what a
   subsequent Send transmits. Staged → Live sets `sentIndex = 0` or to the buffer end, per the
   prompt in §4.4.

#### 5.4.3 Why this unifies the two modes

Staged and Live are the same pipeline with a different flush trigger — Staged is "settle delay =
infinite, flush on Send". One drain implementation, one retraction implementation, one set of
tests. Live mode stops being a special case.

#### 5.4.4 UI

- Sent text is **dimmed with a thin vertical watermark rule** at the boundary; pending text renders
  at normal emphasis. Both cues are non-color-dependent (§4.8).
- Supporting text shows `N pending`.
- A prominent **LIVE** badge (error-container colored) sits in the top app bar whenever live mode
  is armed, so it's never ambiguous that keystrokes are leaving the device.
- **Catch up now** appears in the bottom bar when pending text exists.
- Live mode auto-disables on disconnect, and on app background unless "Keep live typing in
  background" is on.
- Live mode is disabled (with an explanatory tooltip) when no host is connected; tapping it opens
  the device picker.

### 5.5 F-HID-05 · Clipboard send

Types the current clipboard contents. Android 10+ restricts clipboard reads to the focused app, so
this is invoked while the app is visible or from the notification action. Clipboard content is
never persisted or logged.

### 5.6 F-HID-06 · Macros & special keys

A key-pad sheet from the Type bottom bar for keys the staging area can't express:

- `Esc`, `Tab`, `Enter`, `Backspace`, `Delete`, arrows, `Home/End/PgUp/PgDn`, `F1`–`F12`
- Sticky `Ctrl` / `Alt` / `Shift` / `Gui` modifiers + a key tap
- Preset combos: `Ctrl+Alt+Del`, `Alt+Tab`, `Ctrl+C`, `Ctrl+V`, `Win+R`, `Cmd+Space`, `Ctrl+Alt+F2`
- Consumer keys: volume, play/pause, next/prev
- User-defined macros: an ordered keystroke+delay list with a name and icon

Macro output bypasses the buffer and goes straight to the transport (it isn't text, so there's
nothing to stage) — but it's blocked while a drain is mid-flight to avoid interleaving.

### 5.7 F-HID-07 · Foreground service & notification

Shows active device, mode (Staged/Live), pending count or send progress, and actions:
**Disconnect**, **Release all keys**, **Stop live typing**.

### 6.1 F-LLM-01 · Provider configuration

All providers speak the **OpenAI Chat Completions** wire protocol.

```kotlin

    val id: String,
    val name: String,                 // "OpenRouter", "DeepSeek", "Local llama.cpp"
    val baseUrl: String,              // https://openrouter.ai/api/v1

    val showAllModels: Boolean = false, // bypass the non-chat deny-list (§6.1.4)

    val organization: String?,

```

**Presets** shipped (base URL + docs link prefilled, key blank):

| Preset | Base URL |
|---|---|

| DeepSeek | `https://api.deepseek.com/v1` |
| OpenAI | `https://api.openai.com/v1` |

| LM Studio (local) | `http://localhost:1234/v1` |
| Custom | user-entered |

Multiple providers can be configured; one is **active**, switchable from the Chat top bar dropdown
without leaving the screen.

#### 6.1.1 Provider editor (`/settings/llm/{id}`)

Fields in order: name · base URL (validated; warns on plain HTTP unless `allowInsecureHttp`) ·
masked API key · **Test connection** · **model picker** (§6.1.2) · sampling sliders · system
prompt · custom header rows · delete with confirmation.

Configured providers can also be removed directly from the provider list, with
confirmation; removal deletes the provider's stored API key.

**Test connection** saves and uses a newly pasted key, then issues
`GET {baseUrl}/models`. On success, if no default model has been chosen, the
first chat model returned becomes the default before the result is shown. It reports one of:

| Result | Shown as |
|---|---|
| 200 + model list | ✅ "Connected · 47 models · 240 ms" — models cached, picker populated |
| 200 but unparseable | ⚠️ "Connected, but the model list wasn't understood" — falls back to manual entry |
| 401 / 403 | ❌ "Key rejected" — with a link to the provider's key page |
| 404 on `/models` | ⚠️ "This endpoint doesn't list models" — manual entry (§6.1.4) |
| Timeout / DNS / TLS | ❌ Specific cause, not a generic failure |

The base URL is normalised on save: a trailing `/` is stripped, and a missing `/v1` is flagged
(not silently added) since some gateways legitimately omit it.

#### 6.1.2 Model discovery — the dropdown

**Yes — the model list is fetched live from the provider, never hard-coded.** The app calls
`GET {baseUrl}/models`, the OpenAI-standard endpoint every listed provider implements, and
populates a searchable picker from the response.

This matters more than convenience: because nothing is baked into the app, **a model released
tomorrow appears in the dropdown tomorrow** — no app update, no maintained model list going stale.
Whatever DeepSeek's current lineup is when you build this, hitting Refresh shows it.

The picker is a full-screen searchable sheet, not a bare dropdown, because list sizes vary by three
orders of magnitude between providers:

```
┌──────────────────────────────────────────┐
│ ← Select model            [⟳ Refresh]    │
│ ┌──────────────────────────────────────┐ │
│ │ 🔍 deepseek                          │ │
│ └──────────────────────────────────────┘ │
│ [All] [Free] [Tools 🔧] [Vision 👁]      │  filter chips
├──────────────────────────────────────────┤
│  deepseek-chat                        ✓  │
│  128K ctx · $0.14/$0.28 per M · 🔧       │
│  ────────────────────────────────────────│
│  deepseek-reasoner                       │
│  64K ctx · $0.55/$2.19 per M             │
├──────────────────────────────────────────┤
│  ✎ Enter a model ID manually             │
└──────────────────────────────────────────┘
```

Each row shows what the provider actually reported — context length, price per million tokens,
and a 🔧 badge for tool-capable models (§6.1.5). Fields the provider doesn't return are simply
omitted rather than guessed at.

Caching: the list is stored per provider with a fetch timestamp, reused offline, auto-refreshed
when older than 24 h on opening the picker, and force-refreshable with the ⟳ button.

#### 6.1.3 What `/models` actually returns, per provider

The endpoint is standard; its payload is not. Handled per-provider:

| Provider | Auth to list? | Returns | Handling |
|---|---|---|---|
| **OpenRouter** | No | Hundreds of models with rich metadata — pricing, context length, `supported_parameters` | Search is essential; pricing and tool-capability badges come straight from the response; `:free` variants get a Free filter chip |
| **DeepSeek** | Yes | A short list of chat models, minimal metadata | Shown as-is; no filtering needed |
| **OpenAI** | Yes | *Everything* — chat models plus embeddings, TTS, transcription, moderation, image models | Non-chat models filtered out by default (§6.1.4) |
| **Groq / Together / Mistral** | Yes | Chat models mixed with embedding/audio models | Same filtering |
| **Ollama / LM Studio** | No | Locally installed models only | No pricing; list reflects what's pulled locally |
| **Custom / gateway** | Varies | May 404 or return a proxy-specific shape | Graceful fallback to manual entry |

#### 6.1.4 Filtering and the manual fallback

Providers that return non-chat models are filtered with a deny-list of ID patterns
(`embed`, `whisper`, `tts`, `dall-e`, `moderation`, `rerank`, `image`, …). The filter is a
heuristic on model IDs, so it is **user-overridable** — a **Show all models** toggle in the picker
reveals the unfiltered list, and the deny-list is editable in advanced settings for gateways with
unusual naming.

**Manual entry is always available**, and is not a degraded path:

- Providers that don't implement `/models` (some proxies, self-hosted gateways) go straight to it.
- A brand-new model that a provider ships before updating their own `/models` response can be typed
  in directly.
- Private preview / allow-listed model IDs that never appear in public listings work the same way.

A manually entered ID is **not** validated against the list — the app doesn't second-guess you.
It's validated by the first request: a `400`/`404` naming an unknown model surfaces as
"Model `xyz` was rejected by the provider" with a one-tap jump back to the picker, rather than a
generic error.

#### 6.1.5 Capability detection and the agent-typing dependency

Where the provider reports capabilities (OpenRouter's `supported_parameters` and
`architecture.input_modalities` are the richest source), **tool support** (🔧) and **vision
support** (👁) are recorded per model and surfaced as badges with matching filter chips.

This isn't cosmetic — **agent direct typing (§6.3) is built on tool calls.** If the selected model
can't do them, the app falls back to parsing fenced ` ```type-to-host ` blocks, which is less
reliable. So:

- Selecting a model known to lack tool support shows an inline note in the agent control row:
  *"This model doesn't support tool calls — agent typing will use the text-block fallback."*
- Where capability is unknown (most providers don't report it), the app assumes support, tries the
  tool call, and silently falls back on a provider error indicating tools are unsupported —
  recording the result so it doesn't retry the same dead end every turn.

#### 6.1.6 Per-conversation model selection

The active provider/model pair is a global default; the Chat top bar dropdown overrides it **per
conversation**, and the choice is stored on the conversation (§8). Switching model mid-conversation
is allowed and is marked inline in the transcript ("Switched to `deepseek-reasoner`"), so it's
clear later which model produced which reply.

### 6.2 F-LLM-02 · Chat UI

#### 6.2.1 Rendering
- **Bubbles**: user right in `primaryContainer`; assistant left in `surfaceContainerHigh`;
  system/error centered in `errorContainer`.
- **Markdown**: headings, bold/italic, lists, links, inline code, fenced code blocks, tables.
  Code blocks carry a language label, syntax highlighting, and an action row.
- **Streaming**: tokens appended live; expressive `LoadingIndicator` at the tail until first token;
  **Stop generating** replaces Send during streaming.

#### 6.2.2 Sending chat content to the host
- **Per-code-block**: `⌨ Type to host`, `⌨ Type + Enter`, `⧉ Copy`.
- **Per-message**: Copy, **Type to host**, Regenerate, Edit & resend (user messages), Delete,
  Show raw markdown, Token/cost info.
- **Selection typing**: selecting any span in a message reveals a contextual bar with
  **Type selection to host** — arbitrary segments, not just whole blocks or whole messages.
- All three routes push text through the **same staging buffer path** as everything else. Default
  behaviour is a confirm-and-send sheet showing exactly what will be typed; a setting allows
  "Send immediately without preview" for users who want fewer taps. Text from a code block gets
  "strip leading whitespace" applied by default (§3.4.3).
- If no host is connected, these actions open the device picker instead of failing.

#### 6.2.3 Image attachments

Yes — the composer takes images, so you can photograph a host screen and ask what's going on.
This closes the app's most useful loop: **photograph the host → ask the model → type the fix back
over HID**, all without the host having a working network connection or usable input.

##### Sources

| Source | Mechanism | Permission |
|---|---|---|
| **Camera** | System camera app via `ACTION_IMAGE_CAPTURE` | **None** — see note |
| **Gallery** | Android Photo Picker (`PickVisualMedia`) | **None** — the picker grants per-item access |
| **Clipboard** | Paste an image copied elsewhere | None |
| **Share sheet** | The app registers as a `image/*` share target, so a screenshot can be shared into a new or existing chat from anywhere | None |

The share-target route matters more than it looks: taking an Android screenshot and hitting Share →
HID & Seek is the fastest path from "something's wrong on my phone" to "ask the model", and it
works from the screenshot notification without opening the app first.

> **Implementation note — the app needs no permissions at all for images.** The
> Android Photo Picker grants per-item access, and delegating capture to the
> system camera app via `ACTION_IMAGE_CAPTURE` avoids `CAMERA` entirely (an app
> only needs that permission if it declares it, which this one does not).
> Earlier drafts specified in-app `CameraX` capture and a `CAMERA` permission;
> the delegated route is strictly better — one fewer permission to request, one
> fewer to justify, and nothing lost but an in-app viewfinder.

##### Composer UI

- A **＋ attach** button sits left of the text field, offering Camera / Gallery / Paste.
- Attached images appear as a horizontally scrollable **thumbnail strip above the input**, each with
  a remove ✕, a size/token estimate, and tap-to-preview.
- **Crop and rotate** before sending — essential for photos of a monitor, where the useful content
  is a fraction of the frame and the rest is bezel, desk, and glare. Cropping tightly also cuts
  token cost substantially.
- Default cap **4 images per message** (configurable 1–10).
- Sent images render inline in the user's bubble, tappable for a full-screen zoomable viewer.

##### Wire format

Standard OpenAI multimodal content array, so it works with any compatible provider:

```json
{ "role": "user", "content": [
    { "type": "text", "text": "what's this error?" },
    { "type": "image_url",
      "image_url": { "url": "data:image/jpeg;base64,…", "detail": "auto" } }
] }
```

Images are inlined as `data:` URIs rather than uploaded anywhere — there is no first-party
backend, and the image goes only to the user's configured endpoint (§9.3).

##### Processing before send

Applied to every image, in order:

1. **Rotate** per EXIF orientation, so photos aren't sent sideways.
2. **Downscale** to a max edge of **1,568 px** (configurable 512–2,048). Beyond this, providers
   downsample anyway and you pay tokens for nothing.
3. **Re-encode** as JPEG at quality 85 (PNG preserved for screenshots, where text stays crisper).
4. **Strip all EXIF metadata** — including **GPS coordinates**. Non-optional and not user-facing:
   a photo of your desk should never carry your home address to a third-party API.
5. **Enforce a payload ceiling** (default 4 MB per request); exceeding it drops quality
   progressively, then warns rather than silently mangling.

##### Model capability

Vision requires a vision-capable model. Where the provider reports modalities (OpenRouter exposes
`architecture.input_modalities`), vision models get a 👁 badge and a **Vision** filter chip in the
model picker (§6.1.2).

- Attaching an image while a **known text-only** model is selected shows an inline prompt:
  *"`deepseek-chat` can't read images — switch model?"* with a one-tap jump to the vision-filtered
  picker. It does not block you, in case the capability data is wrong.
- Where capability is **unknown**, the app sends and surfaces any provider rejection clearly
  (§10), recording the result so it stops offering images for that model.

##### OCR alternative

An optional **Send as text instead** action on each thumbnail runs on-device text recognition
(ML Kit, bundled, no network) and inserts the extracted text into the message instead of the image.

Worth having for three reasons: it works with text-only models, it costs a fraction of the tokens,
and extracted text can be sent **straight to the host over HID** — retyping a long error code or a
UUID off a screen is exactly the drudgery this app exists to remove. Accuracy on photographed
screens is imperfect, so the extracted text lands in the composer for review, never sent blind.

##### Storage

- Images live in app-private storage, referenced by `MessageAttachmentEntity` (§8), and are
  included in Markdown export as a sibling folder.
- Since **chat history is kept forever** (§6.2.4), images accumulate. `/settings/data` shows
  attachment storage size with **Delete all images** (keeping the messages, replacing each with a
  "image deleted" placeholder) and per-conversation deletion cascades to its images.
- `FLAG_SECURE` applies to the full-screen image viewer when the parent conversation is marked
  sensitive.

#### 6.2.4 Conversations and history

**Chat history is kept forever by default.** There is no automatic expiry, no retention timer, and
no background pruning — nothing is deleted unless the user deletes it.

- Conversations live in a navigation drawer on the Chat screen: title (auto-generated from the
  first message, editable), provider/model badge, last-updated timestamp, search across all
  message content.
- **New chat**, **Rename**, **Duplicate**, **Export as Markdown** (via SAF), **Pin**.
- **Manual deletion at three granularities**:
  1. **Single message** — long-press → Delete. Deleting a user message offers "also delete the
     reply".
  2. **Single conversation** — drawer row overflow → Delete, with a confirmation naming the
     conversation and its message count, and an **Undo** snackbar (soft-delete held 10 s).
  3. **All conversations** — `/settings/data` → **Delete all chat history**, with a typed
     confirmation ("delete") because it's unrecoverable, showing the total conversation and
     message count first.
- Multi-select mode in the drawer allows deleting several conversations at once.
- Deletion is a hard `DELETE` from Room plus a `VACUUM` on the "delete all" path, so content isn't
  recoverable from free pages afterwards. Deleting a message or conversation also deletes its
  attachment files from disk (§6.2.3), not just their database rows.

### 6.3 F-LLM-03 · Agent direct typing

Letting the model type on the host itself.

#### 6.3.1 Control surface and default

A mode selector sits directly above the chat composer, always visible:

| Mode | Meaning |
|---|---|
| **Ask** — **the default, every launch** | The model may *request* a keystroke send; each request surfaces an inline approval card showing the exact text, target device, and estimated duration. Nothing is transmitted until the user taps **Allow**. |
| **Auto** | Requests execute without per-request approval, subject to §6.3.3. Entering Auto requires a confirmation dialog and shows a persistent error-colored banner while active. |
| **Off** | The model cannot request keystrokes at all; the tool isn't advertised to it. Only the user's own "Type to host" actions send anything. |

**Ask is the default and is restored on every app launch.** Auto is a deliberate, in-session choice:
it never persists across launches, never survives a disconnect, and cannot be pre-set as the
startup mode from Settings. Off is available as an explicit user choice but is not the default —
Ask is strictly safer than it in no respect and more useful, since every send still requires a tap.

The selector is disabled with an explanatory tooltip when no host is connected; tapping it opens
the device picker.

#### 6.3.2 Mechanism

An OpenAI-compatible **tool call**, so it works with any provider supporting tools; providers
without tool support fall back to a fenced-block convention (` ```type-to-host `) the app parses.

```json
{
  "name": "type_to_host",
  "description": "Type text on the connected physical device as keyboard input.",
  "parameters": {
    "type": "object",
    "properties": {
      "text":        { "type": "string", "description": "Exact text to type" },
      "press_enter": { "type": "boolean", "default": false },
      "delay_ms":    { "type": "integer", "description": "Optional inter-key delay override" }
    },
    "required": ["text"]
  }
}
```

Secondary tools, same approval model: `press_keys` (named keys/combos, e.g. `ctrl+alt+t`),
`get_host_status` (connection state, layout, LED state — read-only, never gated).

The tool result returned to the model reports success, characters sent, and dropped characters, so
it can adapt.

#### 6.3.3 Guardrails (apply in Ask and Auto)

1. **Hard character cap** per call (default 2,000; configurable 1–10,000).
2. **Rate limits**: max calls per assistant turn (default 3) and per minute (default 10).
3. **Blocklist**: configurable regex list that always requires confirmation, even in Auto.
   Defaults cover destructive shell patterns (`rm -rf`, `mkfs`, `dd if=`, `:(){ :|:& };:`,
   `format `, `del /s`), credential-shaped strings, and `sudo`.
4. **Auto expires** after a configurable window (default 15 min) or on disconnect, reverting to Ask.
5. **Every call is logged** to the audit list (§6.3.4) in all modes.
6. **Kill switch**: notification action "Stop agent typing", plus an optional volume-down long-press,
   immediately reverts to Ask and releases all keys.
7. Agent mode is **never** changed by a settings restore, deep link, tool response, or model
   output — only by direct user interaction with the selector.

#### 6.3.4 Audit log

`/settings/agent` lists the last 200 events: timestamp, device, mode at the time, first 80
characters (redacted for sensitive snippets), full character count, approved/denied, result.
Exportable and clearable.

### 6.4 F-LLM-04 · Context awareness

- History sent up to a configurable token budget, trimmed oldest-first. "Summarize older messages"
  compacts them via one extra model call. **Trimming affects only what is sent to the API — nothing
  is deleted from stored history** (§6.2.4).
- Optional system-prompt preamble injecting host context — device nickname, keyboard layout, host
  OS tag — so the model produces correct commands and shortcuts. Off by default; toggled in
  `/settings/agent`.

#### 7.3.1 Keystroke timing settings

| Setting | Default | Range |
|---|---|---|
| Typing profile | `Normal` | Fast / Normal / Safe / BIOS / Custom |

Each slider shows a live **estimated throughput** readout ("≈ 61 chars/sec · 500 chars in 8.2 s")

#### 7.3.2 Live mode settings

Live mode's batching and safety behaviour, separate from the per-keystroke delays in §7.3.1.
**Every value in the live-typing pipeline is user-configurable with a sane default.** No timing or
safety constant is hard-coded; each is exposed here with an expressive slider or toggle, a plain-
language explainer, and a **Reset to default** action (per-setting and for the whole group).

| Setting | Default | Range | What it does |
|---|---|---|---|
| **Settle delay** | **400 ms** | 0–2,000 ms | How long you must pause typing before pending text is sent. Lower = host keeps up more closely but transmits in tiny bursts and catches words mid-autocorrect. Higher = cleaner batches, host visibly lags. `0` = send as soon as the composing region clears. |
| **Flush on space** | On | On/Off | Send immediately at a word boundary instead of waiting out the settle delay. |
| **Flush on Enter** | On | On/Off | Send immediately on newline. Off is unusual but allowed. |
| **Pending flush threshold** | 120 chars | 20–1,000, or Off | Force a flush once this much text is pending, regardless of the settle delay, so long unbroken input doesn't pile up. |
| **Retraction cap** | **64 chars** | 0–500, or Unlimited | Most Backspace keystrokes sent to the host without asking, when already-sent text changes. Higher rides out large autocorrect rewrites silently; lower bounds how much host text can be wrongly deleted if the host caret has moved. `0` = always ask. |
| **Over-cap action** | Ask | Ask / Always retype / Always skip & resync | What happens when a retraction exceeds the cap. Non-`Ask` values show a confirmation when selected. |
| **On reconnect** | Ask | Ask / Resume drain / Reset watermark | Whether queued pending text is sent after a dropped connection, or the host is assumed out of sync and the watermark jumps to the buffer end. |
| **Keep live typing in background** | Off | On/Off | Whether live mode survives the app going to background. Off auto-disables it. |
| **Warn on mid-text edit** | On | On/Off | Snackbar the first time an edit before the watermark triggers a retraction in a session. |

Two presets sit above the sliders for users who don't want to reason about the individual values:

| Preset | Settle | Retraction cap | Character |
|---|---|---|---|
| **Responsive** | 150 ms | 128 | Host tracks you closely; more corrections visible on the host |
| **Balanced** (default) | 400 ms | 64 | — |
| **Careful** | 800 ms | 16 | Few corrections ever reach the host; noticeable lag; prompts sooner |

Changing any individual slider moves the preset selector to **Custom**. Presets are per-device
overridable, alongside layout and typing profile (§7.2), so a BIOS box and a desktop can carry
different live-mode behaviour.

## 8. Data model

```kotlin
// Room
// NOTE (implemented): the device roster lives in DataStore + kotlinx.serialization,
// not Room. It is a bounded list of a handful of records with no queries, no
// joins, and no full-text search, so Room's value would be unused while its
// cost (KSP codegen, migrations) would be real. Room still earns its place for
// chat history, where message volume and FTS actually need it.
//
// The override fields are nullable on purpose: null means "follow the global
// default", so changing a default moves every device that has not been given an
// explicit answer, while a device pinned to BIOS keeps it.
@Serializable data class DeviceRecord(
    val address: String,
    val name: String, val nickname: String?,
    val layoutId: String?,               // null follows the global default
    val profileId: String?,              // null follows the global default
    val livePresetId: String?,           // null follows the global default
    val hostOs: HostOsTag,               // UNKNOWN, WINDOWS, MACOS, LINUX, ANDROID, IOS, TV, OTHER
    val autoReconnect: Boolean, val isDefault: Boolean,
    val lastConnectedAtEpochMs: Long?, val charsSent: Long,
)

@Entity data class ConversationEntity(
    @PrimaryKey val id: String, val title: String, val pinned: Boolean,
    val providerId: String, val model: String,
    val createdAt: Instant, val updatedAt: Instant,
)

// NOTE (implemented): chat storage is hand-written SQLite, not Room. KSP has no
// build for Kotlin 2.4.10 (its latest targets 2.3.x), so Room's annotation
// processor cannot run at all. Plain SQLite still provides everything this
// feature needs — foreign keys with cascade delete, an FTS4 index kept in step
// by triggers, and VACUUM so "delete all history" reclaims the pages rather
// than leaving content legible in free space. Revisit if KSP catches up.
@Entity(indices = [Index("conversationId")]) data class MessageEntity(
    @PrimaryKey val id: String, val conversationId: String,
    val role: Role,                       // USER, ASSISTANT, SYSTEM, TOOL
    val content: String,
    val toolCalls: String?,               // serialized
    val promptTokens: Int?, val completionTokens: Int?,
    val createdAt: Instant, val error: String?,
)   // FK to ConversationEntity, ON DELETE CASCADE

// Cached model catalogue per provider — populated from GET /models (§6.1.2).
// Every field beyond `id` is nullable because provider payloads vary wildly;
// the UI omits what wasn't reported rather than displaying a guess.
@Entity(primaryKeys = ["providerId", "id"]) data class LlmModel(
    val providerId: String,
    val id: String,                      // provider's exact model ID
    val displayName: String?,
    val contextLength: Int?,
    val promptPricePerM: Double?, val completionPricePerM: Double?,
    val supportsTools: Boolean?,         // null = provider didn't say (§6.1.5)
    val supportsVision: Boolean?,        // null = unknown; drives the 👁 badge (§6.2.3)
    val isFree: Boolean = false,
    val fetchedAt: Instant,
)

@Entity(indices = [Index("messageId")]) data class MessageAttachmentEntity(
    @PrimaryKey val id: String, val messageId: String,
    val localPath: String,               // app-private storage
    val mimeType: String,                // image/jpeg, image/png
    val widthPx: Int, val heightPx: Int, val byteSize: Long,
    val ocrText: String?,                // populated only if OCR was run
    val deleted: Boolean = false,        // bulk image purge keeps the message, drops the file
)   // FK to MessageEntity, ON DELETE CASCADE

@Entity data class SnippetEntity(
    @PrimaryKey val id: String, val name: String,
    val content: String, val sensitive: Boolean, val createdAt: Instant,
)

@Entity data class AgentAuditEntity(
    @PrimaryKey val id: String, val deviceAddress: String,
    val mode: AgentMode, val preview: String, val charCount: Int,
    val approved: Boolean, val result: String, val at: Instant,
)
```

Full-text search over `MessageEntity.content` via an FTS4 shadow table for the conversation search
in §6.2.4.

Settings live in a Proto DataStore (`settings.proto`). API keys live only in
`EncryptedSharedPreferences` keyed by `apiKeyAlias`, backed by an Android Keystore AES-GCM master
key — never in Room, logs, exports, or crash reports.

Transient live-typing state (`sentIndex`, pending region, retraction pending-decision) lives in the
`TypeViewModel` and `SavedStateHandle`; only the buffer text is persisted.

## 9. Permissions, security, privacy

### 9.1 Permissions

| Permission | Why | When requested |
|---|---|---|
| `BLUETOOTH_CONNECT` | Connect to hosts, read device names | First use of the device picker |
| `BLUETOOTH_SCAN` (`neverForLocation`) | Discover nearby hosts | On scan |
| `BLUETOOTH_ADVERTISE` | Be discoverable as a keyboard | On "Add a device" |
| `INTERNET` | LLM API calls | Manifest only |
| `POST_NOTIFICATIONS` | Foreground service notification | First connect |
| `FOREGROUND_SERVICE` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` | Hold the session | Manifest only |

No location permission, no storage/media permission (the Android Photo Picker grants per-item
access, and exports go via SAF), and — thanks to minSdk 31 — **no legacy `BLUETOOTH` /
`BLUETOOTH_ADMIN` permissions and no dual permission path**.

#### 9.1.1 Request timing and denial handling

Every permission is requested **in context, at the moment the feature is first used** — never in a
launch-time gauntlet. Tapping "Camera" asks for `CAMERA`; opening the device picker asks for
`BLUETOOTH_CONNECT`. The user sees why it's needed because they just asked for the thing that
needs it.

- **Rationale before request.** Where `shouldShowRequestPermissionRationale()` is true (the user
  declined once already), an explanatory sheet precedes the system dialog, naming the specific
  capability lost — not a generic plea.
- **Permanent denial** (Android's two-strike rule) replaces the in-feature control with a
  one-tap **Open app settings** deep link, since the system dialog can no longer be shown.
- **Graceful degradation, not breakage.** Denial disables exactly one path and nothing else:

  | Denied | Still works |
  |---|---|
  | `CAMERA` | Gallery, clipboard, and share-sheet attachment |
  | `POST_NOTIFICATIONS` | Everything — the foreground service still runs, silently |
  | `BLUETOOTH_SCAN` | Connecting to already-known and already-bonded devices |
  | `BLUETOOTH_CONNECT` | The entire Chat tab, including images and OCR |

- **No permission is a precondition for launching the app**, and no screen is blocked behind one.
  The Chat tab is fully usable with zero Bluetooth permissions; the Type tab is fully usable with
  zero camera or notification permissions.
- Permissions are never re-requested automatically after a denial — only when the user next
  actively taps the feature.

### 9.2 Security posture

- The app can type arbitrary input into another machine. Every design decision biases toward
  **the user seeing what will be sent before it is sent**: preview sheets, the sent/pending
  watermark, the LIVE badge, per-request approval cards, the audit log, the panic key.
- Agent Auto is opt-in, session-only, time-limited, rate-limited, blocklisted, and loudly indicated.
- Live-mode retraction is capped and prompts before deep rewrites, bounding the damage when the
  host caret has moved.
- TLS enforced by default; plain HTTP only for explicitly flagged endpoints, and never for a host
  outside RFC1918/loopback ranges. Network security config disallows cleartext by default.
- No certificate pinning (users may run local or proxied endpoints).
- API keys and sensitive snippets use per-value AES-GCM authenticated encryption backed by a
  non-exportable Android Keystore key; aliases are bound as authenticated data.
- `FLAG_SECURE` optionally applied to the Type screen when the buffer holds a sensitive snippet.
- R8 with obfuscation on release; no debug logging of buffer or chat content in release builds
  (release logging tree drops below `WARN` and redacts content fields).

### 9.3 Data handling

- Chat content — text **and images** — leaves the device only to the user-configured LLM endpoint,
  stated plainly in the LLM settings screen. Images are inlined into the request, never uploaded to
  any intermediary.
- **All EXIF metadata, including GPS, is stripped from every image before it leaves the device**
  (§6.2.3). This is unconditional and has no opt-out.
- OCR runs fully on-device (bundled ML Kit); choosing "send as text" means the image itself never
  leaves the phone at all.
- No first-party backend. No telemetry unless opted in.
- `allowBackup=false` by default; opt-in backup excludes API keys and sensitive snippets via
  `dataExtractionRules`.
- History is kept forever by design (§6.2.4), which makes the manual deletion controls the primary
  privacy lever — they're surfaced in the Chat drawer, not buried.

## 10. Error handling

| Condition | Behaviour |
|---|---|
| Bluetooth off | Blocking card on Type with "Turn on" action |
| HID profile unsupported | One-time explainer; app still usable for LLM chat, HID actions disabled |
| Registration rejected (another HID app registered) | Explain the conflict, name the likely app, offer retry |
| Connect timeout | Inline row error in the picker + Retry + Bluetooth settings |
| No device connected when a send is attempted | Open the device picker rather than showing a bare error |
| Disconnect mid-send | Halt, report characters delivered, offer "Resend remainder" |
| Disconnect mid-live-drain | Pause drain, keep pending text, badge the pending count as queued |
| Host not accepting reports | After 3 consecutive failures, pause and surface "Host may not be ready" |
| Live retraction exceeds cap | Prompt: Retype from here / Skip and resync / Stop live typing |
| LLM 401 | "Check your API key" + deep link to the provider editor |
| LLM 429 | Backoff + retry indicator, honour `Retry-After` |
| Unknown model ID rejected | "Model `xyz` was rejected by the provider" + one tap back to the picker |
| Image sent to a text-only model | Provider's rejection surfaced as "This model can't read images" + one tap to the vision-filtered picker; capability cached so it isn't offered again |
| Image payload too large (413) | Re-encode at lower quality and retry once, then warn with the size |
| Camera permission denied once | Rationale sheet on next tap, then the system dialog again (§9.1.1) |
| Camera permission permanently denied | Camera row becomes a one-tap **Open app settings** link; gallery, clipboard, and share-sheet paths unaffected |
| OCR finds no text | "No text found in this image" — offer to send it as an image instead |
| `GET /models` 404 or unparseable | Fall back to manual model entry, no blocking error (§6.1.4) |
| Model list stale and device offline | Use the cache, show a "last updated" timestamp on the picker |
| LLM 5xx / network | Inline retry on the failed message |
| Stream interrupted | Keep partial content, mark incomplete, offer Continue |
| Tool call malformed | Do not execute; error bubble with the raw payload |

- [ ] A photo of a host screen can be attached from camera, gallery, clipboard, and the system

- [ ] Chat history survives app restart indefinitely; single-message, single-conversation, and

- [ ] No API key appears in logcat, exports, or crash reports
- [ ] Settings is unreachable from the bottom bar and reachable from both tabs' gear icon
- [ ] Full TalkBack pass on both tabs, the device picker, and the settings tree

### 13.1 Defaults to tune on real hardware

Not blockers. Both are **user-configurable settings with defaults** (§7.3.2), so these are starting
values to revisit after a week of real use, not decisions to make up front.

1. **Live-mode settle delay — 400 ms** (range 0–2,000 ms). How long after you stop typing before
   pending text is sent to the host. Lower feels more instant but produces many tiny transmissions
   and catches words mid-autocorrect; higher batches cleanly but the host visibly lags your typing.
2. **Retraction cap — 64 characters** (range 0–500 or Unlimited). The most Backspace keystrokes the
   app will send at the host without asking first, when already-sent text changes. Higher rides out
   big autocorrect rewrites silently; lower limits how much host text can be wrongly deleted if the
   host caret has moved.

The **Responsive / Balanced / Careful** presets exist so neither number has to be understood to get
sensible behaviour, and per-device overrides mean a BIOS box and a daily-driver desktop don't have
to share one answer.
